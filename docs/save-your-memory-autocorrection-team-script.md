# 자동보정선행개발팀용 `save-your-memory` 발표 스크립트

## 발표 정보

- 발표 자료: [`save-your-memory-autocorrection-team.html`](save-your-memory-autocorrection-team.html)
- 대상: 자동보정선행개발팀
- 권장 시간: 12~15분
- 핵심 목표: `save-your-memory`를 단순 파일 검색기가 아니라 **팀 문서를 검색 가능한 근거로 컴파일하는 도구**로 이해시키기
- 준비물: VS Code, GitHub Copilot 로그인, Python 3.11 이상, 데모용 비민감 문서 폴더와 `.env`

## 발표 전 준비

1. HTML 파일을 브라우저에서 엽니다. `docs/assets/openclaw-brain-overdrive.png`는 표지에서 상대 경로로 로드되므로 저장소 폴더 구조를 유지합니다.
2. 오른쪽 화살표 또는 `Space`로 다음 슬라이드, 왼쪽 화살표로 이전 슬라이드, `Home`/`End`로 처음·끝 이동합니다. `F`는 전체 화면입니다.
3. 실제 사내 문서나 개인 경로를 화면에 띄우지 않습니다. 별도 데모 폴더나 테스트 fixture를 사용합니다.
4. 실제 Copilot 시연을 할 경우 질문을 실행할 workspace에 `.env`를 미리 준비합니다. `SAVE_YOUR_MEMORY_HOME`은 원본 폴더 밖의 임시 생성 경로로 지정합니다.

예시 `.env`는 발표 중 화면에 직접 띄우기보다 다음처럼 설명만 합니다.

```dotenv
SAVE_YOUR_MEMORY_ROOT="D:\Demo\Knowledge"
SAVE_YOUR_MEMORY_HOME="D:\SaveYourMemoryData"
```

## 전체 진행 멘트

### 1. 표지: 문서를 근거로 바꾸는 법

**권장 시간: 45초**

**말할 내용**

> 오늘 설명드릴 `save-your-memory`는 새로운 문서 저장소를 하나 더 만드는 도구가 아닙니다. 이미 팀이 가지고 있는 로컬 문서 폴더를 읽고, 검색용 카탈로그와 원본 링크가 있는 Markdown 위키로 컴파일합니다. 오늘은 기능 목록부터 보지 않고 `Who, What, Why, Where, When` 다섯 질문으로 이 도구가 우리 팀에 어떤 자리를 차지하는지 설명드리겠습니다.

**강조할 점**

- 표지의 가재 이미지는 제품 기능을 설명하는 이미지가 아니라 저장소에 이미 있는 시각 자산입니다.
- 핵심 단어는 `근거`입니다. 답변 자체보다 어디서 확인할 수 있는지가 중요합니다.

### 2. 5W 한 장 요약

**권장 시간: 50초**

**말할 내용**

> 한 문장으로 요약하면, 팀이 가진 Windows 파일 트리를 SQLite FTS5 카탈로그와 Markdown 위키로 컴파일하고, Copilot이나 Codex가 그 결과를 읽어 출처와 함께 답하게 하는 로컬 우선 지식 플러그인입니다. `Who`는 팀과 답변 에이전트, `What`은 카탈로그와 위키, `Why`는 재탐색과 근거 추적 문제, `Where`는 Root·Home·Chat의 경계, `When`은 인덱싱부터 점검까지의 운영 순간입니다.

**전환 멘트**

> 이 다섯 요소를 각각 조금 더 구체적으로 보겠습니다.

### 3. WHO: 누가 쓰는가

**권장 시간: 1분**

**말할 내용**

> 첫 번째 사용자는 자동보정선행개발팀입니다. 설계 조건, 보정 알고리즘, 캘리브레이션 기록, 시험 결과처럼 파일로 쌓이는 지식을 질문합니다. 두 번째 역할은 `save-your-memory` 자체입니다. 이 도구는 문서를 대신 판단하거나 수정하지 않고, 검색 가능한 구조를 만듭니다. 세 번째 역할은 Copilot과 Codex입니다. 이들은 답변 계층으로서 검색 결과와 원본 경로를 읽고 설명합니다.

> 따라서 이 도구의 책임 경계도 분명합니다. 팀이 지식의 소유자이고, 인덱서는 컴파일러이며, Copilot은 근거를 바탕으로 답변을 만드는 계층입니다.

**팀에 연결하는 질문**

> 우리 팀에서 같은 시험 조건이나 설계 결정을 찾기 위해 여러 폴더를 열어본 경험이 얼마나 있는지 떠올려 보시면 됩니다.

### 4. WHAT: 무엇인가

**권장 시간: 1분**

**말할 내용**

> 입력은 기존 원본 파일 트리입니다. 안전하게 스캔한 뒤 텍스트, Office, PDF 등 지원되는 형식의 내용을 추출합니다. 결과는 두 표면으로 나뉩니다. `index.sqlite3`는 SQLite FTS5 기반 검색 카탈로그이고, `wiki/sources/`는 파일별 Markdown provenance 페이지입니다.

> 여기서 중요한 점은 본문을 파일마다 무제한으로 복제하는 구조가 아니라는 것입니다. 기본 32 KiB 청크로 검색하고, 위키 페이지에는 원본 절대 경로·상대 경로·추출 상태·해시·추출 방식이 남습니다. 검색 결과에서 위키를 거쳐 원본을 다시 확인할 수 있습니다.

**정확한 표현**

- “모든 파일 내용을 이해한다”가 아니라 “읽을 수 있는 내용을 추출하고 읽기 상태를 기록한다”고 말합니다.
- 바이너리나 변환기 없는 레거시 PPT는 경로·메타데이터 검색이 남을 뿐, 본문을 이해하는 것은 아닙니다.

### 5. WHY: 왜 필요한가

**권장 시간: 1분 10초**

**말할 내용**

> 팀 문서가 늘면 검색은 두 문제로 나뉩니다. 첫째, 파일이 어디 있는지 찾는 문제입니다. 둘째, 답을 찾은 뒤에도 그 답이 어느 원본에서 왔는지 확인하는 문제입니다. 일반적인 파일 검색은 첫 번째 문제 일부만 해결합니다.

> `save-your-memory`는 질문을 카탈로그에 보내고, 상위 wiki 페이지에서 근거를 좁힌 뒤, Copilot이 원본 경로와 함께 설명하도록 흐름을 고정합니다. 목표는 AI가 팀을 대신 결정하는 것이 아니라, 팀원이 이미 가진 자료를 더 빨리 재발견하고 검토하게 하는 것입니다.

**한 문장 요약**

> 우리가 자동화하려는 것은 판단이 아니라 재탐색입니다.

### 6. WHERE: 어디에 놓이는가

**권장 시간: 1분**

**말할 내용**

> 안전성을 위해 Root와 Home을 반드시 분리합니다. Root는 실제 원본 문서가 있는 폴더이며 읽기 전용입니다. Home에는 `index.sqlite3`와 `wiki/`가 생성됩니다. Home이 Root와 같으면 설정 오류로 거부됩니다.

> VS Code Copilot을 사용할 때는 질문을 실행하는 workspace의 `.env`가 중요합니다. `.env`에는 실제 Windows 경로가 들어가므로 Git에 커밋하지 않습니다. 생성 데이터와 원본 자료도 공개 저장소에 넣지 않습니다.

**안전 문장**

> 이 도구는 원본을 복사해 편집하는 시스템이 아니라, 원본을 건드리지 않고 별도 결과를 만드는 시스템입니다.

### 7. WHEN: 언제 쓰는가

**권장 시간: 1분 10초**

**말할 내용**

> 처음에는 `index`로 전체 자료를 만듭니다. 이후에는 문서가 추가·수정·삭제됐을 때 같은 `index`를 다시 실행하면 변경된 항목 중심으로 반영합니다. 새 변환기를 설치해 이전에 읽지 못한 PDF나 PPT를 다시 시도할 때는 `--retry-unreadable`을 사용합니다.

> 실제 질문은 `query`가 담당하고, 현재 카탈로그의 파일 수와 오류는 `status`, 위키의 누락·고아 페이지는 `lint`로 확인합니다. 이 도구는 백그라운드 실시간 watcher를 전제로 하지 않습니다. 데이터가 바뀌면 명시적으로 `index`를 다시 실행해야 합니다.

**전환 멘트**

> 이제 실제로 질문 한 줄이 어떤 계층을 통과하는지 보겠습니다.

### 8. 검색 흐름

**권장 시간: 1분 20초**

**말할 내용**

> 첫 단계는 질문을 임의의 짧은 키워드로 바꾸지 않고 사용자의 자연어 그대로 검색하는 것입니다. 두 번째는 FTS5 검색입니다. 긴 문서는 청크로 나뉘고, 여러 청크가 맞아도 파일당 상위 결과 하나로 합칩니다.

> 우리 팀에 특히 중요한 개선은 한글 검색입니다. `온도보정알고리즘`처럼 붙여 쓴 복합어와 `온도 보정 알고리즘`처럼 띄어 쓴 질문 사이를 문자 bigram으로 보완합니다. AND 검색이 전혀 성립하지 않을 때는 OR 폴백으로 일부 근거를 찾지만, 더 정확한 AND 결과가 있을 때 단일어 노이즈로 결과를 희석하지 않습니다.

> 세 번째 단계에서 Copilot은 보통 상위 1~3개 wiki 페이지를 읽습니다. 마지막으로 확인된 주장만 답하고, wiki와 원본 파일을 Sources로 남깁니다. 근거가 없으면 없다고 말하는 것이 정상 동작입니다.

### 9. 팀 활용 질문

**권장 시간: 1분**

**말할 내용**

> 검색 품질은 질문의 형태에도 영향을 받습니다. 단순히 “온도 보정 찾아줘”라고 하기보다, 조건·변경 이력·원본 경로를 요청하면 결과를 검토하기 좋습니다.

> 예를 들어 “온도 보정 알고리즘의 설계 조건과 변경 이력을 원본 링크와 함께 요약해줘”라고 물을 수 있습니다. 시험 재현을 위해서는 캘리브레이션 기준, 입력 조건, 합격 기준을 각각 어느 문서에서 찾았는지 요청합니다. 변경 영향이 궁금하면 새 보고서를 먼저 인덱싱한 뒤 기존 자료와 차이를 묻습니다.

**주의할 점**

> “차이를 찾아줘”는 검색과 요약을 요청하는 것이지, 시스템이 자동으로 설계 변경의 안전성을 승인한다는 뜻은 아닙니다. 최종 판단은 팀 리뷰가 담당합니다.

### 10. Copilot 사용법

**권장 시간: 1분 10초**

**말할 내용**

> VS Code에서는 Command Palette의 `Chat: Install Plugin From Source`에서 GitHub 저장소 URL로 설치합니다. Plugins에서 활성화한 다음 Copilot Chat을 Agent 모드로 바꿉니다. `/`를 입력하면 `/save-your-memory:save-your-memory` 스킬이 보입니다. 플러그인 이름과 스킬 이름이 같아서 두 번 반복되는 것이 정상입니다.

> 최초 실행 때는 Python CLI를 실행할 Terminal tool 승인이 나올 수 있습니다. 대상이 이 플러그인의 `scripts/save_your_memory.py`인지 확인하고 승인합니다. 그 뒤 “처음부터 내 자료를 인덱싱해줘”, “온도보정알고리즘 자료를 원본 링크와 함께 찾아줘”, “위키 상태와 누락 페이지를 검사해줘”처럼 자연어로 요청하면 됩니다.

**실제 설치 전제**

- 최신 VS Code와 GitHub Copilot 로그인
- Python 3.11 이상 및 SQLite FTS5
- 질문을 실행하는 workspace의 `.env`

### 11. 안전 계약

**권장 시간: 1분**

**말할 내용**

> 검색 편의보다 먼저 합의할 것은 원본 보호와 데이터 경계입니다. `SAVE_YOUR_MEMORY_ROOT` 아래 원본은 수정·이동·삭제하지 않고, symlink·junction·reparse point도 따라가지 않습니다. SQLite와 Markdown 위키는 Root와 분리된 Home에만 생성합니다.

> 읽지 못한 파일은 숨기지 않습니다. `unsupported`나 `error` 상태와 파일 경로를 남기고, 본문을 이해했다고 주장하지 않습니다. `.env`, 개인 문서, 로컬 원본 경로와 생성 데이터는 공개 저장소에 올리지 않습니다.

> 이 계약 덕분에 팀은 편리한 검색과 원본 보호를 함께 가져갈 수 있습니다. 다만 Home 접근 권한과 화면 공유 시 로컬 경로 노출은 운영자가 별도로 관리해야 합니다.

### 12. 기능 전체

**권장 시간: 1분**

**말할 내용**

> Copilot Chat은 자연어를 받지만 내부 계약은 네 가지입니다. `index`는 전체 또는 변경분을 반영합니다. `query`는 검색 근거를 JSON으로 돌려줍니다. `status`는 카탈로그 상태를 보여줍니다. `lint`는 wiki 일관성을 확인합니다.

> 읽기 실패 파일을 새로 지원하려면 `index --retry-unreadable`을 사용합니다. 이 옵션은 이전에 `unsupported` 또는 `error`였던 레코드만 다시 시도합니다. 상태와 lint는 검색과 별개인 운영 점검이므로 정기적으로 실행하는 것이 좋습니다.

**보여줄 명령**

```powershell
python scripts/save_your_memory.py --env-file .env index --json
python scripts/save_your_memory.py --env-file .env index --retry-unreadable --json
python scripts/save_your_memory.py --env-file .env query "온도 보정 알고리즘" --limit 5 --json
python scripts/save_your_memory.py --env-file .env status --json
python scripts/save_your_memory.py --env-file .env lint --json
```

### 13. 도입 판단

**권장 시간: 1분**

**말할 내용**

> 이 도구가 잘 맞는 경우는 문서가 로컬 Windows 폴더에 흩어져 있고, 답변에 파일 위치와 근거 링크가 중요하며, 팀이 Copilot 또는 Codex를 사용하고 있는 경우입니다.

> 반대로 이미지 전용 문서의 OCR, 암호화·손상 PDF 복구, 변환기 없는 레거시 PPT 본문 이해, 문서 간 진실성 판정, 실시간 파일 감시는 이 도구의 기본 역할이 아닙니다. 이런 제한을 숨기지 않고 도입 범위를 정해야 합니다.

> 도입은 작은 비민감 폴더 하나로 시작합니다. 대표 질문 세 개를 정하고, 검색 결과의 wiki 링크와 원본 경로를 확인하고, `lint` 결과를 검토한 뒤 범위를 늘립니다.

### 14. 마무리

**권장 시간: 40초**

**말할 내용**

> 오늘의 결론은 세 가지입니다. 첫째, `save-your-memory`의 사용자는 팀과 답변 에이전트입니다. 둘째, 산출물은 검색용 SQLite와 근거용 Markdown 위키입니다. 셋째, 가장 중요한 가치는 AI가 똑똑해지는 것이 아니라 팀원이 문서를 다시 찾고 원본을 확인하는 비용이 줄어드는 것입니다.

> 다음 단계로 민감하지 않은 문서 폴더 하나를 정하고, 실제 질문 세 개로 시험해 보겠습니다. 결과가 맞는지뿐 아니라 답변이 wiki와 원본 링크까지 남기는지 함께 검토하면 됩니다.

## 데모 진행 순서

발표 중 실제 Copilot Chat을 시연한다면 다음 순서를 권장합니다.

1. 준비된 workspace와 `.env`가 있다는 것만 확인하고, 실제 경로 값은 가립니다.
2. Agent 모드에서 `/save-your-memory:save-your-memory`를 선택합니다.
3. “처음부터 내 자료를 인덱싱해줘. 추가·변경·오류 건수를 알려줘.”라고 요청합니다.
4. 인덱싱 결과의 오류·unsupported 파일을 확인합니다. 읽지 못한 파일을 이해했다고 말하지 않는지 봅니다.
5. “온도 보정 알고리즘의 설계 조건과 원본 링크를 찾아줘.”라고 검색합니다.
6. 답변의 `Sources`에서 wiki 페이지와 원본 파일 링크가 모두 있는지 확인합니다.
7. “위키 상태와 누락·고아 페이지를 검사해줘.”라고 요청합니다.
8. 새 변환기를 설치한 상황을 설명할 때만 `--retry-unreadable` 재시도를 시연합니다.

## 예상 질문과 답변

### “벡터 검색이나 의미 검색인가요?”

현재 핵심 검색 엔진은 SQLite FTS5 기반 lexical search입니다. 기본 청크·BM25·파일 단위 병합과 한국어 bigram 보강을 사용합니다. 외부 임베딩 서버나 LLM API를 필수로 요구하지 않습니다.

### “원본 파일을 안전하게 보존하나요?”

원본 Root 아래 파일은 읽기 전용으로 처리하고, symlink·junction·reparse point를 따라가지 않습니다. 다만 운영자는 Root와 Home을 분리하고 `.env`와 생성 데이터의 접근 권한을 별도로 관리해야 합니다.

### “읽을 수 없는 파일은 어떻게 되나요?”

파일명·상대 경로·크기·수정 시각·추출 상태를 가진 레코드로 남습니다. 본문을 추출하지 못한 파일을 이해했다고 주장하지 않습니다. 변환기를 나중에 준비했다면 `--retry-unreadable`로 재시도합니다.

### “문서가 바뀌면 자동으로 반영되나요?”

백그라운드 실시간 감시가 아니라 명시적 `index` 실행 방식입니다. 변경되지 않은 파일은 size/mtime 기반으로 다시 추출하지 않습니다.

### “문서 두 개가 서로 모순되면 어느 쪽이 맞나요?”

검색 결과와 provenance를 보여줄 수 있지만, 문서의 진실성이나 최신성에 대한 최종 판정은 자동으로 하지 않습니다. 팀의 리뷰와 문서 상태 관리가 필요합니다.

## 발표 후 팀에 남길 한 문장

> `save-your-memory`는 팀의 문서를 대신 결정하는 AI가 아니라, 팀이 가진 근거를 다시 찾고 확인하게 해 주는 로컬 문서 컴파일러입니다.
